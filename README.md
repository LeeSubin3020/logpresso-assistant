# Logpresso Assistant

로그프레소(Logpresso) 공식 쿼리 매뉴얼과 사내 쿼리 자료를 먼저 검색하고, 그 내용을 근거로 **쿼리 작성**과 **오류 진단**을 도와주는 RAG(검색 기반 답변) 어시스턴트입니다. Streamlit 웹 화면에서 질문하거나 오류 화면 캡처를 붙여넣어 사용합니다.

> 이 저장소에는 코드만 들어 있습니다. 지식베이스(`data/`)는 이전 회사의 업무 자료라 포함하지 않았습니다. 실행하려면 직접 준비한 문서로 지식베이스를 만들어야 합니다.

## 기능

| 기능 | 설명 |
|---|---|
| 쿼리 작성 | 자연어 질문을 로그프레소 쿼리와 설명으로 변환. 근거가 부족하면 추측하지 않고 되묻습니다. |
| 오류 진단 | 오류 메시지나 실행한 쿼리를 넣으면 매뉴얼의 명령어·오류 코드 섹션을 찾아 원인과 해결 방법을 안내합니다. |
| 화면 캡처 입력 | 오류 화면 이미지를 붙여넣으면 글자를 읽어 검색어로 씁니다. |
| 출처 표시 | 답변에 참고한 자료 이름과 유사도를 함께 보여줍니다. |
| 질문 기록 | 질문·답변·출처를 로컬에 저장해 기록 탭에서 확인합니다. |

## 동작 방식

```
질문 (+ 오류 화면 캡처)
  → [캡처가 있으면] 이미지 속 오류 메시지·쿼리를 텍스트로 판독
  → 하이브리드 검색: 로컬 임베딩(multilingual-e5-base) 의미 검색 후보 32개
       → 질문 키워드 일치율로 재정렬 (0.65 × 의미 + 0.35 × 키워드) → 상위 8개
  → [진단 모드] 질문에 나온 명령어·오류 코드로 공식 매뉴얼 섹션을 직접 찾아 근거에 추가
  → 검색된 근거 + 답변 규칙을 담은 프롬프트로 Claude API 호출
  → 쿼리·설명(또는 진단·해결 방법)과 참고 출처 표시
```

- 문서 임베딩과 검색은 로컬 CPU에서 처리하고, 외부 API는 이미지 판독과 답변 작성에만 사용합니다.
- 모델을 직접 학습시키지 않고, 문서를 추가한 뒤 색인만 다시 만들면 답변에 반영됩니다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `app.py` | Streamlit 화면, 이미지 전처리·판독, Claude API 호출 |
| `prompts.py` | 문법 요약, 모드별(쿼리 작성 / 오류 진단) 시스템 프롬프트 |
| `retriever.py` | ChromaDB 하이브리드 검색 (의미 + 키워드) |
| `manual_lookup.py` | 공식 매뉴얼을 명령어 단위로 나눠 명령어·오류 코드로 직접 조회 |
| `sync_docs.py` | `data/docs/`의 PDF·txt·md → `data/docs_kb.jsonl` (전화번호·이메일 마스킹) |
| `sync_obsidian.py` | Obsidian 노트 폴더 → `data/obsidian_kb.jsonl` (같은 마스킹 적용) |
| `chunk_documents.py` | `data/*.jsonl`을 1,500자 청크로 분할 → `data/chunks.jsonl` |
| `build_index.py` | 청크 임베딩 → `data/chroma_db/` (바뀐 청크만 다시 임베딩, `--full`이면 전체) |
| `logger.py` | 질문·답변 기록 (`data/query_log.jsonl`) |
| `학습.bat` / `실행.bat` | 색인 만들기 / 앱 실행 (Windows) |
| `eval/` | 쿼리 정확도 비교 도구 (아래 참고) |

## 실행 방법

```powershell
python -m pip install -r requirements.txt
```

1. `data/docs/`에 매뉴얼·쿼리 자료(PDF, txt, md)를 넣습니다.
2. `학습.bat`을 실행해 색인을 만듭니다. (처음 한 번은 임베딩 모델을 내려받습니다.)
3. `실행.bat`을 실행하고, 사이드바에 Anthropic API 키를 넣거나 환경변수 `ANTHROPIC_API_KEY`를 설정합니다.

### 지식베이스 형식

`data/` 아래의 `*.jsonl` 파일은 한 줄에 문서 하나입니다.

```json
{"source": "문서 이름", "folder": "분류", "content": "본문", "n_chars": 1234, "redacted": false}
```

오류 진단 모드의 매뉴얼 직접 조회(`manual_lookup.py`)는 `data/knowledge_base.jsonl`에서 `folder`가 `official_manual`로 시작하는 문서를 공식 쿼리 매뉴얼로 사용합니다.

## 정확도 비교 (`eval/`)

로그프레소 테스트 서버에 테스트용 로그(방화벽 60건, 웹 접속 40건)를 만들고, 같은 질문 28개에 대한 각 도구의 쿼리를 서버에서 실제로 실행해 정답 쿼리의 결과와 비교했습니다. 사용법은 [eval/README.md](eval/README.md)에 있습니다.

| 대상 | 정답 (28문항) |
|---|---|
| GPT (웹 채팅) | 19 |
| Gemini (웹 채팅) | 16 |
| 같은 모델에 검색 없이 질문 | 28 |
| 이 어시스턴트 (개선 전) | 21 |
| 이 어시스턴트 (개선 후) | 28 |

- 개선 전에는 정규식 파싱 문항을 틀렸습니다. 프롬프트의 명령어 목록에 `rex`가 빠져 있어 `replace()`로 답했고, 서버에서 매치되지 않았습니다. 목록에 추가한 뒤, 개선 중 보지 않은 새 문항 12개에서 정답이 8개에서 12개로 늘었습니다.
- 같은 모델에 검색 없이 물어도 28개를 모두 맞혀, 이 질문 세트(기본 쿼리 위주)에서는 검색의 효과가 드러나지 않았습니다. 검색의 효과는 사내 자료가 있어야 답할 수 있는 질문으로 확인해야 합니다.
- 결과 파일: `eval/results/report.html`, `eval/results/results.csv`. 각 시스템의 원본 답변은 사내 자료 이름이 섞여 있어 포함하지 않았습니다.
- `eval/examples/`는 채점기가 동작하는지 확인하려고 만든 가상 답변입니다.
